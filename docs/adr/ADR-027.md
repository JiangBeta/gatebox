# ADR-027：组件生命周期边界与升级本体

- 状态：已接受
- 日期：2026-09-14
- 关系：修订 ADR-001（控制面 + 独立外部组件）、延续 ADR-002（Caddy 配置生效方式）、加固 ADR-011（工具安装归属）

## 背景

需求要求 GateBox「管理第三方工具的版本、升级，实施操作，读取反馈」，与 ADR-001 的「不接管其生命周期」正面冲突。同时 Caddy 模块（如 Coraza）必须 `xcaddy` 编译期注入、设备端无 Go 工具链；Docker 由系统包管理器管理、需要 root。需要为「生命周期」建立精确本体，才能界定哪些能管、哪些不能管。

## 决策

### 1. 生命周期六层

| 层 | 定义 | 归属 |
|---|---|---|
| 配方 Recipe | 制品构成（二进制版本 + 编译进的模块） | 上游官方 |
| 制品 Artifact | 配方产出的可执行文件 | 上游构建 |
| 制品源 Source | `official` / `custom` / `system` 三通道 | 分档 |
| 运行态 Runtime | 进程启停、健康、日志、恢复 | GateBox |
| 配置 Config | 读写配置、热加载 | GateBox |
| 版本 Version | 读当前版本、查源最新版（只读） | GateBox |
| 升级 Upgrade | 用新制品替换旧制品 | 边界 |

### 2. 边界规则

> **GateBox 管理「进程」与「配置」，观测「版本」，但永不改写「配方」。升级 = 用上游发布的制品替换旧制品——GateBox 只当搬运工，不当配方师。**

- Coraza 只能作为**已发布制品变体**存在（官方或用户自建并发布的制品），设备端不编译。用户在 GateBox 外自行编译 coraza-caddy 并放入自己的 `custom` 源，是合法路径。
- ADR-001 由「全局规则」修订为「默认模式之一」：组件分 `managed`（GateBox 供应+管理）与 `attached`（用户/系统提供，GateBox 只读写配置/API）。

### 3. 组件 vs 被管对象

- `dockerd` 是**组件**（attached，不纳管）；**容器/镜像/网络/卷**是**被管对象**（GateBox 全权操作）。
- 因此「不接管 Docker」精确表述为：不接管 dockerd，但全权接管容器。

### 4. 升级本体

- 制品源三通道：`official`（上游官方）、`custom`（用户/团队 fork，如自编译 caddy）、`system`（包管理器）。
- 「最新版本」永远相对于源通道解析。
- 升级策略三档：`replace`（下载→校验→原子替换→健康检查→失败回滚）、`system`（只提示，不自我替换）、`none`。
- 升级失败回滚复用 ADR-002「先校验、失败回退」模式。

## 后果

- 优点：升级需求被满足，同时守住「不自行改变运行逻辑」的安全边界；Coraza/Docker 两个难题均有明确归属。
- 代价：需要 `source` 抽象与三通道实现；OpenWrt 上需处理与包管理器共存（`system` 档组件永不自我替换）。
