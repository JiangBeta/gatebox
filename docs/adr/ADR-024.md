# ADR-024：统一 DNS 凭证模型（acme.sh 签发 + ddns-go 上报共用）

- 状态：已接受
- 日期：2026-09-07
- 前置：ADR-003（DNS 凭证双向下发 cloudflare/dnspod/aliyun）、ADR-013（acme.sh 接管签发）

## 背景

PRD v2 要求「DNS 供应商凭证相关功能需与 DDNS 共用」。现状：`DNSCredential` 已统一存储（ADR-003），但使用侧——acme.sh 签发（`acme.providerEnv`，`dns_dp/dns_cf/dns_ali`）与 ddns-go 上报（GO 接入）——各自持有 provider 映射，无显式的「一套凭证两用」语义。

## 决策

1. **`DNSCredential` 是唯一凭证模型**：不新建 DDNS 专用凭证表；供应商集合沿用 cloudflare / dnspod / aliyun（含 dnspod.cn 不为 .com）。
2. **一个凭证两条使用侧**：
   - **签发侧**（acme.sh）：`internal/acme/providerEnv`（已实现：DP_ID/DP_KEY、CF_Token、ALI_KEY/ALI_SECRET）。
   - **上报侧**（ddns-go）：`internal/ddns` 生成 ddns-go 配置段时，从同一 `DNSCredential` 取供应商与 token（ddns-go 的 provider 名近似映射，见 `docs/domain.md` §9 任务 4）。
3. **UI 语义**：凭证表单注明「同时用于证书签发与 DDNS 上报」；「验证」按钮调 `POST /credentials/verify`（存量的 provider 可连通性探测）。
4. 供应商元数据（卡片图标、动态 token 字段、provider 名映射表）收敛为**单处定义**（models 或 config），签发/上报两侧共用，消灭两处硬编码漂移。

## 后果

- 优点：一份凭证管理，acme 与 ddns-go 天然一致；后续新增供应商只改一处元数据。
- 代价：两套外部工具的 provider 参数名不同，映射表需维护且随版本验证。
- 约束：凭证加密（conf/secret.key）覆盖两使用侧；凭证删除需校验无引用（域名或路由）。
