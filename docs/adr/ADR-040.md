# ADR-040：应用网关统一框架（统一描述 / 可观测 / 声明式调和）

- 状态：已接受
- 日期：2026-09-17
- 前置：ADR-027（生命周期边界）、ADR-028（组件运行时接口）、ADR-031/032（前后端分层）、ADR-036（扩展平台）、ADR-037 ~ ADR-039（插件拔插化）
- 修订：ADR-020 中「每 handler 硬编码渲染、不做通用 key-value」的适用范围（限定为 Caddy 片段 / handler 参数等自由文本；顶层业务对象必须 schema 化）

## 背景

GateBox 是「可扩展应用网关」，由多个**异质组件**（caddy / docker / acme / ddns-go / mosdns / 未来插件）构成。本项目参考 [oxidns](https://github.com/SvenShi/oxidns) 的前端与配置模型（单一真相 `config.yaml` + 每个插件一份 schema → 全 UI 派生），但二者**不对称**：

- oxidns 的对象**同质**（插件只有一根轴 `kind`）、**一份真相**（config.yaml）、**一种生效模型**（热重载）；
- GateBox 的对象**异质**：至少两根正交轴（**组件轴** vs **领域实体轴**），存储真相不唯一（BoltDB 领域模型 / 逐项目 compose 文件 / 派生插件配置 / gatebox.conf），生效语义多样（热载 / 重启 / 部署 / 重签发）。

设计前的代码测绘结论：

1. 组件间信息流转是**隐式**的：docker label → 派生 Service（`gateway/derive.go`）→ Caddyfile → `/load` → acme 签发（`handler/gateway_api.go` 的 `reloadCaddy`），但**无显式依赖图、无失效追踪、无 reconcile**。
2. 传播靠**全量重算**：同一个 `reloadCaddy` 被 20+ 写 handler 调用，「是否触发」取决于 handler 里有没有写调用，导致已知缺陷：改 Domain / Credential 不触发重载、Port 保存需手动重启、改 Variable 不回填已落盘 compose。
3. 已有资产可复用：`extension.Registry` + `Provider` + `Capability`（核心与插件同构，I1 ~ I3 不变式）、投影 API（`since/wait` 长轮询 + `revision`）、扩展点 `config-sync` / `reconcile` / `validator` **已声明但未实现**（`internal/extension/extension.go` 的扩展点常量、`internal/plugin/plugin.go` 的 `providerFor` 未编译）。

因此需要一套**统一框架**，把「统一描述、可观测、声明式调和」三条能力建立在同一份描述之上。

## 决策

### 0. 总框架：一份描述，两条能力（读 / 写）

```
                        可扩展应用网关
                               │
        ┌──────────────────────┼──────────────────────┐
        │                      │                      │
   统一描述（模型层）   ──读──▶  可观测（读取面）        │
        │                      │                      │
        └──────────写─────────▶  声明式调和（执行面）  ──┘
                               │
                承载层：BoltDB · Registry/Provider · 投影 · 组件适配器
```

三条能力**共用同一份「组件描述符」**，故天然不漂移。

### 1. 统一描述（模型层）

**目的**：让异种组件以同一方式被描述，成为整体的一部分。

#### 1.1 组件（Component）

被 GateBox 纳入并统一管理、承担某项网关能力的**功能提供者**。内建组件（caddy / docker / acme …）与外部插件**同构**，核心不认插件身份（延续 ADR-036 I1）。GateBox 不接管其生命周期实现（ADR-001 / ADR-027），只**描述、触发、观测**。

#### 1.2 组件描述符（Component Descriptor）

用统一方式重新描述组件的一份契约，是系统**唯一的描述真相**。构成 = **身份** + **功能清单** + **四契约**：

| 契约 | 内容 | 服务于 |
|---|---|---|
| **配置契约** | 可编辑字段 schema（类型 / 校验 / 文档） | 编辑（Form / YAML） |
| **信息契约** | `consumes` / `produces`（信息端口） | 功能地图与信息流 |
| **观测契约** | `state` / `activity` / `logs` / `metrics` | 可观测 |
| **生效契约** | `actions`（可执行操作）+ `effect`（收到某类信息变更时的自动动作）+ 幂等 / 顺序约束 | 声明式调和 |

> **对 ADR-020 的修订**：ADR-020 的「每 handler 硬编码渲染函数、不做通用 key-value」**仅适用于 Caddy 片段 / handler 参数等自由文本**；顶层业务对象（Service / PortBinding / 凭证…）必须 schema 化。

#### 1.3 功能（Function）

网关对外提供的一项能力（代理 / TLS / 解析 / DDNS 上报 / 容器运行时 / 端口接入 …）。**功能与组件是多对多**（caddy 同时提供代理、TLS、监听）。功能是功能地图的**语义主节点**。

#### 1.4 事实（Fact）

可寻址、被持久化的**期望态单元**（`Service#id`、`Domain#id`、`Credential#id` …）。分三类：

| 类别 | 定义 | 例 |
|---|---|---|
| **持久事实** | 可寻址、落库、期望态、调和可写 | Service(manual) / Domain / Credential / Fragment / Variable / PortBinding / ComposeInstance |
| **派生事实** | 有 ID、可作边端点、可展示，但**不落库**，由事实 + 运行态推导 | docker 从 label 派生的 Service |
| **运行信息** | 只在流上传递、表达「某类数据」，不可寻址 / 不持久 | 容器状态与 IP、证书文件、label |

> **派生事实不可被调和写入**，只能改其源头（如 compose 文件）——这条决定调和「能写什么、只能读什么」。

#### 1.5 信息（Info）

在组件间**流转的类型化数据**（label / domain / cert / port / variable / ip）。来源 = 事实的投影，或组件运行时产出。信息是**边的载荷**。

> **分类按角色，不按值**：同一实体可同时是「事实」与「某类信息的来源」（Domain 是事实，`domain` 信息是它的投影）。

#### 1.6 功能地图（Function Map）

由 **组件 + 功能 + 信息流** 构成的**全景图**，是系统骨架视图。提供**双层投影**：

- **组件视角**（系统 / 排障）：节点 = 组件，节点内列功能端口；
- **功能视角**（人 / 总览）：节点 = 功能，边 = 信息流，节点下标注实现组件。

**状态归属规则**：状态 / 活动 / 日志**挂在组件**；功能节点上的状态 = 其实现组件状态的**聚合**（如「证书」功能的红绿灯 = acme 的状态）。

### 2. 可观测（读取面）

**目的**：把「系统正在发生什么」变得可见、可下钻。它是描述与运行态的**投影，不新增独立数据源**。

| | 静态（是什么） | 动态（正在发生什么） |
|---|---|---|
| **整体** | 功能地图（结构） | 传播轨迹（一次变更的传播与结果） |
| **局部** | 组件（配置 / 版本 / 健康） | 组件内部（当前活动 / 步骤 / 日志） |

观测由**观测契约**提供：

- `state`：静态健康枚举（`healthy / degraded / error / running / stopped / unknown`）；
- `activity`：当前任务与所处步骤（「acme 执行到哪一步」）；
- `logs`：组件内部痕迹 / 日志来源；
- `metrics`：定量指标（QPS / 延迟 / 连接 / 缓存命中 …）。

> `metrics` 不可省，否则「可观测」退化为只有红绿灯；`activity` 是「执行位置」的数据来源。

### 3. 声明式调和（执行面）

**目的**：由「意图 + 图 + 生效契约」**推导**操作，而非预先写死每一步。

#### 3.1 三个输入

- **意图（Intent）**：只声明「哪个事实变了」（what changed），不含如何传播。
- **依赖图（Dependency Graph）**：由**信息契约端口 + 事实间引用**推导出的「消费关系」图。**算出来的，不是画出来的** → 不会像文档一样腐化。
- **生效契约（Effect Contract）**：组件声明的「收到某类信息变更时做什么」（`update-config / restart / hot-reload / reissue / deploy`），含**幂等性**与**顺序约束**。

#### 3.2 调和器（Reconciler）

level-triggered 通用算法（对齐 ADR-036 §6「投影与调和」）：

```
采集期望态 → 推导依赖图 → 求变更事实的消费闭包
→ 按生效契约生成动作 → 拓扑排序（生产者先于消费者）→ 执行 → 记录 Run/Step
```

性质：**幂等、可重放、周期兜底**（捕捉外部漂移：证书文件出现、docker daemon 状态变化）。写操作只做两件事：**落库事实 + `Trigger()`（去抖合并）**。

**自动传播示例**（「不预先写死」的样本）：删除某代理 → 图中该 Service 的 `domain` 边存在 → 触发 ddns 的 `effect`（删除域名 + 重启）；ddns 的「删域名」本身又是一次事实变更 → 递归推导 → 触发 ddns 重启。同一套机制跑两层，而非两段写死代码。

#### 3.3 运行记录（Run / Step / Event）

一次调和的执行轨迹，三层 + 日志：

| 层 | 内容 | 用途 |
|---|---|---|
| **Run** | `{runId, 触发意图, 触发类型(intent/periodic/manual), 起止, 总状态}` | 整体动态 |
| **Step** | `{component, action, status, 起止, error, 前驱}` | 图上节点 / 边着色（默认粒度） |
| **Event** | 步骤内细粒度事件（如 acme：DNS 记录已添加 / 等待验证 / 证书已下载） | 当前执行位置 |
| **Logs** | 独立连续流，用 `runId` / `stepId` + 时间戳关联，**不结构化塞入 Run** | 下钻细节 |

> Run 必须能**脱离意图**（periodic reconcile / 健康轮询 / 手动操作），故需**触发类型**字段。

#### 3.4 收敛（Convergence）

使现实逐步等于期望：**幂等重放 + 失败重试 + 漂移检测**；**不引入 DB 回滚**，改以「状态可见」表达不一致（调和自愈优于事务回滚）。

### 4. 与扩展平台的衔接（不重造）

| 框架概念 | 承载（现有资产） | 状态 |
|---|---|---|
| 组件描述符 | `extension.Provider` + manifest | 需扩展 |
| 功能 / 能力 | `extension.Capability` / `Point*` | 已有 |
| 配置契约 | `extension.ProviderField`（凭证） | 需泛化 |
| 信息契约 | —（`consumes` / `produces`） | 待长 |
| 观测契约 | `HealthCollector` / 组件日志 / metrics | 需统一 |
| 生效契约 | `PointReconcile` / `PointConfigSync` + 组件 apply | 已声明未实现 |
| 事实 | `model.*`（BoltDB） | 已有 |
| 信息 | `ProjectionInput` / `ProxyRule` / `projectedDomain` | 已有局部 IR |
| 依赖图 | —（推导） | 待长 |
| 调和器 | `reloadCaddy`（待泛化） | 需泛化 |
| 运行记录 | `model.CertLog` + 前端 TaskCenter | 种子 |

插件接入调和器的两种模式（遵守 ADR-036 I2「核心 → 插件只经投影」）：

- **config-sync 型**：核心从投影渲染插件配置 → 落盘 → 触发进程重启（核心编排）；
- **reconcile 型**：核心只 bump `revision` + 通知，插件侧车拉投影自行收敛（自收敛）。

### 5. 不变量与边界

**不变量**：

1. **单一描述、单一真相**：描述符是契约，不是文档；
2. **边由端口 + 数据推导**，不由手写；
3. **一切界面是描述符 / 图的投影**（Form / YAML / 卡片 / 拓扑 / 状态同源）；
4. **观察不改变执行，执行可被观察**；
5. **组件平等**：内建与插件同构；
6. **密文只以引用出现**，不进统一模型。

**边界（不做）**：

- **不统一存储真相源**：各自保留（BoltDB / 原生文件 / 派生），描述符只**声明真相源在哪**；
- **不做「万能 schema」**：自由文本（Caddy 片段）只做语法高亮 + 校验；
- **不接管组件生命周期实现**（ADR-001 基调不变）。

### 6. 分期（对应 architecture.md §15）

| 层 | 交付 | 依赖 |
|---|---|---|
| **L1 静态自描述** | 组件描述符 + 功能地图 + 静态信息流图（只读、可点开） | 描述符契约 + 边推导 |
| **L2 运行态观测** | 观测契约 + 组件状态 / 活动 / 日志聚合到图上 | 统一的观测契约 + 状态聚合 |
| **L3 执行可追踪** | Run / Step / Event + 调和器 + 传播轨迹回放 | 执行侧埋点 + 实时事件流 |

## 后果

- **优点**：把隐式流转显式化；顺带修掉 Domain / Credential / Port / Variable 的触发缺口；异种组件统一纳入；为可观测与自动化提供同一底座；插件接入只需声明描述符，无需改核心。
- **代价**：描述符由「三契约」扩为「四契约」（配置 / 信息 / 观测 / 生效）；引入「派生事实」与「双层投影」；后端需新增描述符与依赖图的元数据来源；内核执行需从「全量重算」走向「图驱动调和」（L3）；需与 ADR-020 的措辞对齐。
- **范围**：本 ADR 只定**框架与定义**；描述符的具体数据结构、依赖图推导算法、调和器实现、前端派生引擎等，另立单位级设计与实现 ADR。
