# ADR-020：网关机制层决策（健康检查 / 日志 / Handler / Caddyfile 生成）

- 状态：已接受
- 日期：2026-08-31

## 背景

ADR-018/019 定下领域模型与跨单位联动后，需补齐网关的机制层：active health check 如何读、代理日志真相源、Handler 参数建模、Caddyfile 生成器与 Admin API 客户端的最小形态。本轮 grilling 就这四项作出决策。

## 决策

1. **Active Health Checks**：route 增加可选 `healthUri` 字段，**默认 `/`**（兑现「默认开启」），编辑里可设空 = 关闭（避免对「`/` 返回 404 的后端」误报红）。健康状态（绿/红）由后端**单例采集器轮询** caddy Admin API 聚合成快照，前端轮询快照端点——不逐行实时查 caddy（复用 `docker/stats` 的采集器模式）。

2. **日志真相源**：Caddyfile 全局块用 `log` 指令把 access log 写文件（JSON、含 `host` 字段）+ error log 同目录（`$DATA_DIR/tools/caddy/logs/`）。后端按 `host=` + 时间窗过滤 tail，走 **WebSocket follow**（复用 docker 日志交互模式）；历史搜索后置。

3. **Handler 清单与参数**：第一期内置清单 **4 个**——`encode`（Gzip/Br）、`basic_auth`（Basic Auth）、`header`（增删响应头）、`rewrite`（路径改写）；`redir`/`request_header` 后置。参数 schema 采用**每 handler 硬编码一个渲染函数**（Go 结构体 + 前端表单模板），不做通用 key-value（handler 语义差异大，通用化易生成非法 Caddyfile）。`basic_auth` 密码走 **AES-GCM 加密**（复用 DNSCredential / Registry 方案），前端只回传 `HasSecret`。

4. **Caddyfile 生成器 + Admin API 客户端**：全局默认集用 Caddy **snippet** `(gatebox-default)`，各 site block `import gatebox-default`（不内联重复写）；停用 route = **不生成**该 site block（实体保留、可恢复）；Admin 客户端最小实现 **`POST /load`**（原子加载 + 校验失败回退，ADR-002）+ 健康状态读 **`GET /reverse_proxy/upstreams`**；用户扩展点 `import <user 目录>/*` 放在**每个 site block 末尾**，全局块不再重复 import。

## 后果

- 优点：健康状态不逐行打爆 Admin API；日志可按域名过滤；Handler 渲染可控可单测；Caddyfile 结构清晰、用户手改有固定落点。
- 代价：健康快照有一定延迟（轮询周期）；日志写文件占用磁盘（需 logrotate 或后置清理）；每新增 handler 要写一套渲染函数。
- 约束：采集器需处理 caddy 未启动 / Admin API 不可达的降级（健康列显示「未知」而非误报红）；`basic_auth` 生成 Caddyfile 时的 bcrypt 哈希在开发期确定。
