# ADR-017：创建应用（编排）Form↔YAML 编辑器设计

- 状态：已接受
- 日期：2026-08-28

## 背景

Docker 单位的「创建应用」是本体的编排（ComposeInstance）编辑入口。原编辑器为单栏弹层 + 表单/YAML 二选一 Tab；新设计升级为「两栏 + 结构化控件」的富表单（见 `docs/Docker--创建应用的前端界面及功能说明.md`）。本轮讨论（grilling）就其中的跨单位落点、compose 语义映射、默认值策略等作出决策。

## 决策

1. **术语**：左侧「应用」= compose service，UI 文案统一「服务」；「编排名称」= projectName、「展示名称」= displayName。glossary 的「App（应用）」保持网关语义（可代理单元）不动，避免与 Docker 侧「服务」撞名。
2. **域名访问 = caddy label（不建 ProxyRoute 实体）**：域名访问落成 `caddy`/`caddy_1` label（复用现有 caddyRoutes 机制），根域名/凭证读已实现的 Domain API；不提前建网关的 App/ProxyRoute 模型。密码访问（basic_auth）本期隐藏，随网关单位实现。
3. **创建后状态 = 部署动作**：compose 无「定义但默认不启动」的服务级持久字段；「启动/仅创建」是部署动作——「保存并部署」=`up -d`，「仅创建」=`docker compose create`。表单不设此项。
4. **关联网络 external 语义**：加入现有网络 → 顶层 `networks: {名: {external: true}}` + 服务引用；创建网络 → 项目内私有网络。顶层 `networks:`/`volumes:` 由结构化控件自动生成维护。
5. **资源字段单机定位**：非 swarm，用 `shm_size`/`cpus`/`mem_limit`/`gpus`（以 `docker compose config` 实测为准）。
6. **默认值落盘策略**：用户不碰不写；等于 docker 默认值不写（`shm_size: 64m` 不写）；非默认必须写（日志 `max-size`/`max-file` 非 docker 默认，健康检查 docker 无默认）。
7. **depends_on 语义**：只列本编排内 service（compose 限制），跨编排启动顺序依赖不做。

## 后果

- 优点：不提前引入网关数据模型；label 契约最小且向后兼容；YAML 保持最小、往返 diff 干净。
- 代价：域名访问的「访问端口 80/443」「密码访问」等为展示/占位，完整路由语义待网关单位定契约。
