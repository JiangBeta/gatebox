# ADR-037：主程序与插件分离（拔插式插件、统一安装面、生命周期三档与 GateBoxStore）

- 状态：已接受
- 日期：2026-09-16
- 前置：ADR-027（生命周期边界）、ADR-028（组件运行时）、ADR-029（插件模型与分发）、ADR-030（核心/插件分类）、ADR-031（后端分层）、ADR-036（扩展平台）
- 取代：ADR-036「本阶段实现边界」中关于 **sidecar 运行时 / L1 UI 宿主 / 在线索引下载 / 权限强制** 的延迟限制（机制本体不变）
- 后续：ADR-038（核心组件配方变体）、ADR-039（插件运行时契约）

## 背景

ADR-029 / ADR-036 已经确立了「manifest 数据 + 通用引擎 + 贡献注册」的插件模型，但**插件仍然编译在主程序里**，无法独立安装 / 卸载 / 升级：

- 插件目录 `builtinCatalog()` 是 Go 硬编码数组（`backend/internal/plugin/plugin.go:438`），新增插件必须改核心代码并重新编译；
- 插件页面、专属 API 路由、导航入口全部写死在主程序（`frontend/src/router/index.ts`、`utils/toolRoutes.ts`、`handler/mosdns.go`）；
- `manifest.v2.schema.json` 与 `registry/` 只是数据模型占位，**运行时从不加载**，`source.FetchIndex` 无任何调用点；
- 卸载不彻底：`Manager.Remove` 不删除制品、不还原被替换的核心二进制（`plugin.go:297`）；
- 权限 `permissions` 只声明、从不执行；控制面 API 零鉴权（`server.go:47`）。

产品侧需要三类插件：

1. **核心插件扩展**：为核心组件补充能力，可能需要替换核心组件的二进制（例：`caddy-l4` 给 Caddy 增加 TCP/UDP）；
2. **独立进程**：自带二进制与页面，独立运行并由专属页面控制（例：`mosdns`）；
3. **Docker 商店**（下一步）：预置 compose 基础配置，用户只填域名等个性化信息即可运行。

本 ADR 解决前两类的分离问题；第三类归 `catalog`（应用模板目录），不纳入插件契约。

## 决策

### 1. 分离判据：产品主闭环

**判据 = 是否属于产品主闭环「应用 → 域名 → Caddy 反代 → 自动 HTTPS」。**

| 归属 | 内容 |
|---|---|
| **内核保留** | 通用引擎：扩展平台（能力注册表 / 投影 API）、组件运行时（进程 / 健康 / 日志）、制品源（下载 / 校验 / 原子安装）、manifest 解析与贡献编译、生命周期与持久化、动态 UI 宿主（路由 / 菜单 / iframe 桥）；以及 core 三件套适配：`caddy` / `acme` / `docker`（含 `docker-compose`） |
| **迁出为插件** | `ddns-go` / `mosdns` / `flame` / `tailscale` / `caddy-l4` / `coraza` / `geoip` / `realip` 等，连同其 adapter、handler、前端页面、导航与路由声明、静态资源 |

迁移完成后，主仓库只保留**通用引擎 + schema + 样例**，不再包含任何具体插件的业务代码。

### 2. 统一可安装单元

`plugin` 成为**唯一可安装单元**，安装 / 启停 / 卸载 / 权限只有一个入口：

| 部件 | 变更后职责 |
|---|---|
| `component.CoreRegistry` | 降级为「核心组件目录」（caddy/acme/docker），仅存内核不可卸载组件 |
| `plugin.Manager` | 升级为统一安装面；`kind:process` 的插件复用组件进程托管器，不新建进程机制 |
| `extension.Registry` | 保持为贡献 / 能力表；核心与插件同构注册 |

不新增大注册表、不做大爆炸重构。三种 `kind`（`caddy-module` / `process` / `config-only`）语义不变，行为差异全部由 `contributions` 与 `artifacts.role` 导出，不新增引擎分支。

### 3. 三类产品分类 → 契约映射

| 产品分类 | 契约形态 | 制品 | 有独立进程 | 有独立页面 |
|---|---|---|---|---|
| 核心插件扩展 | 声明式贡献（`component-variant` + `renderer`） | 替换核心组件配方的**变体制品**（见 ADR-038） | 否 | 通常 L0 元数据驱动 |
| 独立进程 | `process` + sidecar 契约 + `ui` 贡献 | 自带后端二进制 + UI 制品 | 是 | 是（L0/L1） |
| Docker 商店 | 不适用（归 `catalog` 应用模板） | compose 模板 + 变量 schema | — | — |

**关键结论**：核心插件扩展**不需要**独立的页面逻辑进程——它是「中性特征声明 + 核心组件配方变体 + 可选声明式贡献」。逻辑超出声明式表达能力时，才用 `kind:process` 的 sidecar 承载（ADR-039）。

### 4. 生命周期三档与回滚

「拔插式」要求卸载干净、可回滚：

| 档 | 行为 |
|---|---|
| `disable` | 保留制品与配置，仅停用效果（从注册表注销贡献） |
| `uninstall` | 删除 `$DATA_DIR/tools/<id>/` 制品 + 注销贡献 + **重算/恢复核心组件配方** + **保留用户配置与密钥**（标记「已卸载，数据保留」） |
| `purge` | 二次显式确认后，删除配置与密钥 |

- 被 `component-variant` 替换的核心组件二进制，卸载时**必须触发配方重算**（回到剩余特征集对应的变体或纯核心组件），绝不残留无法解释的二进制；
- 落地真正可用的 `versions/` 目录（`$DATA_DIR/tools/<id>/versions/<key>/`），至少保留上一可用版本以支持回滚（当前代码只有单份 `.bak`，`versions/` 仅存在于文档）。

### 5. 扩展 API 版本化与兼容政策

- 内核维护整数 `extensionApi` 版本；manifest 以 `requires.extensionApi` / `requires.gatebox` 声明依赖；
- 语义化规则：贡献点**新增可选字段 = minor**；**删除或改变字段语义 = major**（升 major 必须先写 ADR）；
- 内核启动时校验，不满足 `requires.gatebox` 的 manifest **拒绝加载**并给出中文提示；
- 在线索引每个版本记录其 `extensionApi`，客户端过滤不兼容项。

### 6. GateBoxStore：定位与权威关系

新增独立公开仓库 **`JiangBeta/GateBoxStore`**（本文档产出其骨架与 AGENTS.md）：

```
GateBoxStore/
├── plugins/<id>/{manifest.yaml, ui/, backend/, assets/, README.md}
├── schema/{manifest.v2.schema.json, catalog.v1.schema.json}   # vendor 自主仓库
├── cmd/gbx-store/               # 维护工具：index（生成索引）/ pack（打包）/ variant-key
├── scripts/build-variant.sh     # xcaddy 构建核心组件变体
├── variants.yaml                # 配方变体清单（CI 回填 url/sha256）
├── .github/workflows/           # 校验 / 插件发布 / 变体构建 / Pages
├── index.json                   # 静态索引（GitHub Pages）
├── docs/                        # 插件作者文档
└── AGENTS.md / README.md
```

- **权威关系**：扩展契约（schema + 本系列 ADR）**权威在主仓库**；Store **vendor 一份并在 CI 校验版本一致**，防止漂移。面向插件作者的说明文档由 Store 自行维护。
- Store **不引入 submodule**；两仓只靠 `extensionApi` / schema 版本契约关联。
- Store 为 **public**：插件索引与制品需匿名可拉取。若未来需要私有仓库，另设带 token 的索引拉取方案。

### 7. 内置插件磁盘化

主仓库不再硬编码内置插件目录。内置插件（随包分发）以 **manifest 文件随包落盘**，运行时从磁盘加载；在线插件从 `index.json` 拉取。二者走同一解析与状态机。

## 本阶段实现边界

**实现**：分离（代码迁出）、统一安装面、生命周期三档、`versions/` 回滚、扩展 API 版本化、磁盘 manifest 加载、在线索引拉取（sha256 校验）、磁盘化内置插件目录、ADR-038 的配方变体、ADR-039 的 sidecar / UI 宿主 / token / dns-provider。

**预留不实现**：制品**签名验签**（minisign/cosign）、L2 远程 ESM、权限授予 UI、cgroup/命名空间隔离、控制面管理鉴权（单管理员登录）。字段在 manifest / catalog 中保留。

## 迁移试点（判据与顺序）

按三条不同路径验证：

| 试点 | 验证路径 | 完成判据 |
|---|---|---|
| `mosdns` | 独立进程：sidecar 后端 + L1 iframe UI + API 反代 | 删除 `adapter/mosdns`、`handler/mosdns.go`、`MosdnsView.vue` 及其路由 |
| `caddy-l4` | 核心插件扩展：`component-variant` 配方替换（ADR-038） | 从主仓库移除其 manifest 与模板 |
| `cloudflare/dnspod/aliyun` | acme 扩展：抽为 `dns-provider` 插件（ADR-039 §5） | 内核 5 处硬编码收敛为注册表 |
| `ddns-go` | 数据型：既有 `config-sync` 投影契约 | adapter 迁出，仅留契约调用 |

**全部完成判据**：`plugin.go:438` 硬编码 catalog 清空为磁盘加载；`frontend/src/utils/toolRoutes.ts` 删除；主仓库仅剩通用引擎 + schema + 样例。

## 后果

- 优点：插件真正可独立安装 / 卸载 / 升级；核心不含插件身份与业务代码；统一安装面；卸载可解释、可回滚；为 Docker 商店预留扩展空间。
- 代价：引入 sidecar 进程托管与 API 反代；插件分发需要额外仓库与 CI；卸载语义变复杂（三档 + 配方重算）；需要在迁移期维持新旧两条路径的兼容。
