# ADR-043：V4.1 批次 4 实施裁定（类型目录 / 路由后端 / 生效链 / 旧数据迁移 / 前端骨架）

- 状态：草案（已裁定，实施中）
- 日期：2026-09-27
- 前置：ADR-041（架构 V4）、ADR-042（V4.1 统一模型）
- 配套设计：
  - [views.md](../v4.1/views.md) — 视图结构（§6 列表列规格 / §7 抽屉 / §12 原型清单已按本文订正）
  - [_naming.yaml](../v4.1/model/_naming.yaml) — 命名映射、推进批次、conventions 已按本文落定
  - [catalog.yaml](../v4.1/model/catalog.yaml) — 最小类型目录（内嵌数据源）
  - [route.yaml](../v4.1/model/route.yaml) / [service.yaml](../v4.1/model/service.yaml) — 批次 4 对象模型
  - [records.md](../v4.1/records.md) — 保留策略已与实现对齐
- 范围：V4.1 批次 4（中间件 / 服务 / 路由）+ 其前置的类型目录最小集，以及本轮实施所需的迁移、任务中心、前端骨架。本文**不改动** ADR-042 已定的模型骨架，只在其留白处做实施裁定。

## 背景

ADR-042 定下了 V4.1 的统一模型（描述符 / 对象 / 蓝图 / 链 / 记录），但有几处**留白**在进入实施时必须先裁定，否则模型文件与实现会各写各的：

1. **批次依赖倒置**：`_naming.yaml` 原本把「类型目录」放在批次 2（`deferred`），而批次 4 的中间件 / 服务 / 路由三者的 `type` 字段都引用它。不先解决就写不了 schema。
2. **路由与服务的引用方向未定**：`views.md` §5 说「项目 → 服务 → 路由」，`views.md` §6 又要求路由列表的「后端」列显示 `ip:端口`——地址该存在哪，谁也没说。
3. **「保存后生效」没有落点**：`views.md` 说保存后生效，但现有 `reconcile` 是基于 `component` 接口的 Caddy 调和，与 V4.1 的通用对象层不是一回事。
4. **运行库里是 8MB 真实数据**，旧表结构与新对象模型不一致（`renames` 给了映射，但 `Service旧` 同时含「接入」和「后端」，拆分规则未定义）。
5. **前端有两套骨架并存**（`src/app` + `src/views`），且主题接错（`App.vue` 的 `ConfigProvider` 拿不到 `design/tokens.ts` 的 `antdTheme`）。

以下逐条裁定。

## 决策

### 1. 类型目录：最小集随批次 4 一并交付（`go:embed`，只读）

- **决定**：类型目录从批次 2 提前到批次 4 交付，但**只装 caddy 内置类型**；插件提供的类型在 `catalog.yaml` 里保留 `installed: false`，界面置灰 + `[安装]`，实际安装留批次 2。
  - `service_types`：已装 `reverse_proxy` / `file_server` / `redirect` / `respond`；待装 `l4_proxy`。
  - `middleware_types`：已装 `encode` / `basic_auth` / `headers` / `websocket` / `rewrite` / `code`。
  - `entrypoint_protocols`：已装 `http` / `https` / `grpc` / `websocket` / `php`；待装 `tcp` / `udp` / `mysql` / `ssh`。
- **交付方式**：`catalog.yaml` 经 `go:embed` 编译进二进制，启动时解析进内存，**本轮无写接口**。与既有 `web/dist` 内嵌模式一致，零新增机制。将来要做在线增删时，本文件即「内置种子」。
- **理由**：本轮的核心交付物是对象层与 schema 驱动表单，不是类型管理。现在凭空设计「内置 vs 用户自定义」的覆盖规则没有真实用例。批次 2 有了组件自述再定不迟。

### 2. L4 类型命名统一为 `l4_proxy`

- **决定**：四层转发**合一**为 `l4_proxy`（`caddy-l4` 插件），用 `network` 参数（`tcp` / `udp`）区分传输协议。**废弃** `tcp_proxy` / `udp_proxy` 两个类型。
- **理由**：原型里 `mock.js` 用 `l4_proxy`（带 `network`），`catalog.yaml` / `index.html` 的 `typeLabel` 用 `tcp_proxy` / `udp_proxy`，同一概念两个名字且两侧都只实现了一半。合一后只有一个类型、一处 label、一套 fields。
- **影响**：`blueprint.md` §2.1、`glossary.md` 路由/服务类型词条已同步。ADR-042 §13 的原始表述**保留不改**（ADR 是当时决策的历史记录，由本文取代其命名部分）。

### 3. 路由是自足对象：后端地址存在路由上（`route.backend`）

- **决定**：`route.backend = { host, port }` 随路由保存；`route.service` 改为**可选**引用。
- **服务引用仅用于两件事**：① 列表「后端」列第二行显示「主机名 · 服务名」；② 健康检查关联。
- **理由**：
  1. `views.md` §5 说「路由 = 一个转发，后端 = 1 个端口」——这个「1 个端口」是路由的固有属性，不该绕道服务才能知道。
  2. `l4_proxy` 这类 L4 转发本来就没有 HTTP 上游服务，原先 `route.service: required` 与它直接矛盾。
  3. `views.md` §6 要求后端列显示 `ip:端口`；若地址在服务上，路由列表要跨对象 join 才能渲染这一列。
- **代价（已知并接受）**：一个服务端口被 N 条路由共用时，改端口要动 N 处。但这本来就是**不同转发**的语义——3 条路由指向同一上游，它们是 3 条独立的转发规则，目标地址本就该独立可配。
- **连带修正**：`views.md` §6「类型」列改为**派生列**（有 service 取 service.type，无 service 则由 entrypoint 协议族推导）；§7 抽屉头部去掉 `[类型▾]`（类型属于服务）。

### 4. 保存后生效：落库 → 标未生效 → Trigger → 最小渲染器 → 回写状态

- **决定**：保存只落库并把 `status.state` 置为 `未生效`，随即 `reconcile.Trigger`；Run 内调用一个**明确标注为最小实现**的 Caddyfile 渲染器，编译加载成功后回写 `已生效`，失败回写 `错误`。
- **理由**：直接同步写 Caddyfile（绕过 Run）会让保存路径成为临时实现，换 reconcile 时全部重写。走 Run 的好处是任务中心从第一天就有真实历史。
- **明确的完成度边界**：本轮渲染器**只覆盖** `reverse_proxy` 单上游 + `middlewares` 列表 + `tls` + `entrypoint` 的基本形态；复杂中间件 `config` 嵌套对象留 TODO。这意味着本轮保存后**可能编译失败**——那是 `status.state=错误` 的真实用例，不是 bug。
- **不做什么**：本轮不做蓝图 revision / diff / rollback（那是批次 7）。

### 5. 旧数据：一次性迁移脚本，先 dry-run，验收通过后执行

- **决定**：按 `_naming.yaml` 的 `renames` 段写迁移脚本，`Service旧` 拆成「接入（域名/端口）→ 路由」与「后端（host:port）→ 服务」。**本轮只交付 `--dry-run` 报告**（将迁移 N 条 / 冲突 M 条 / 无法映射 K 条），执行留到本轮验收通过后作为独立步骤，且幂等、执行前自动备份 `gatebox.db`。
- **理由**：8MB 真实配置不能选「新页面看不见」（会造成配置丢失的错觉），也不该选「全部只读」（本轮的 schema 驱动表单就没有东西可验证）。分两步走让迁移有独立的验收与回滚窗口。

### 6. 任务中心纳入本轮，升级面板不做

- **决定**：本轮做**任务中心**（`GET /api/v1/runs` + SSE `/api/v1/runs/stream`），消费决策 4 产生的真实 Run。**升级按钮保留但置灰** + 「即将推出」。
- **理由**：决策 4 选 C 的直接收益就是 Run 有真实出口。升级面板依赖版本策略（ADR-042 未定），本轮做会引入未决设计。
- **顶栏动作组**三键（任务 / 升级 / 重启）布局因此成立。重启按钮**仅提示手动重启**，不做后端自重启。

### 7. 前端切到 `src/modules`，本轮迁三页 + 主题 + 布局

- **决定**：新建 `modules/{layout,theme,objects,catalog}` 与 `modules/pages/gateway/{RoutePage,ServicePage,MiddlewarePage}`；`App.vue` 换上新 `ConfigProvider`（接 `design/tokens.ts` 的 `antdTheme`），旧 provider 保留但不再注入；路由表分流——六个新一级路径走新骨架，未迁移的旧路径继续走旧 `views/`。
- **理由**：本轮已定要修主题（双主题 + CSS 变量）。若新页面走 `modules`、主题修复留在 `App.vue`/旧 `views/`，两套主题变量会打架（旧组件直接写死颜色）。让「布局 + 主题 + 三页」在同一套骨架下闭环，本轮交付物才自洽。
- **旧 `views/` 一行不删**，逐页退役。

## 影响

**正面**
- 批次 4 的依赖拓扑不再倒置；类型目录、服务、路由三个模型文件可以一致地驱动 schema 表单。
- 路由自足后，路由列表不再需要跨对象 join 渲染后端列。
- 保存路径从第一天就有 Run 记录与状态回写，任务中心不是空壳。
- 主题修正在新骨架上闭环，不会与旧组件样式打架。

**代价 / 风险**
- Caddyfile 最小渲染器覆盖有限，本轮保存可能编译失败（已定为 `状态=错误` 的真实用例）。
- `Service旧` 拆分是迁移里最易出错的一步，靠 dry-run 报告专门列出拆分冲突。
- 主题改造触及 `App.vue` / `main.ts` / 路由表，回归面大于其他前端任务；旧 `views/` 短期仍在，需保证不分流到的页面不白屏。
- 类型目录无写接口：新增自定义类型必须改代码重新编译（批次 2 解决）。

**与 ADR-042 的关系**
本文不改动 ADR-042 的模型骨架，只裁定其留白处（类型目录时机、路由后端归属、生效链落点、旧数据接入、前端骨架）。ADR-042 §13 的 `tcp_proxy` / `udp_proxy` 命名被本文 §2 取代，其余条款继续有效。

## 验证

- 类型目录：19 个模型 YAML 全部可解析；`GET /api/v1/catalog` 返回三张类型表 + `fields` 定义。
- 对象层：curl 全 CRUD 断言；悬空引用被拒；重命名级联。
- 生效链：保存后 `state` 经历 `未生效 → 已生效 / 错误`；Run 与 Step 可查。
- 迁移：`--dry-run` 报告交用户审阅，**不自动执行**。
- 前端：`pnpm typecheck` / `pnpm lint:style` / `pnpm build`；typecheck 与 lint 覆盖全 `src`（存量问题记 baseline，禁止新增）。
- 全部验证通过后才重启服务（重启前须重新构建二进制；改过前端须先 `pnpm build`，`go:embed` 是编译期嵌入）。
