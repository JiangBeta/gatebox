- 范围：重设计 V4 主视图。本文定义 GateBox 的统一模型，作为「蓝图构建」与系统实现的共同基础。

## 背景

- V4 的「功能地图」（`/topology`）是一张**只读的派生关系图**：看得到组件间的数据流，但既不反映真实流量与健康，也没有配置入口。结论：**无监控意义、不能改配置**，判定为失败设计。
- 对照 OxiDNS，其成立依赖两件事：① 一次 DNS 查询只有一条路径（一个 `DnsContext` 在一条 `sequence` 上流动）；② 这条路就是它自己跑的。所以它的「地图」=「执行路径」，天然有监控意义、点开可改。
- GateBox 是**应用网关**，以 Caddy 为核心：用户访问的流量路径基本由 Caddy 定义与执行；GateBox 不拥有 Caddy 的运行时，只做**配置 / 触发 / 观测**。
- 用户要求：模型要**能用、能扩展、可理解**，且所有说明必须配例子。

---

## 决策

### 0. 总纲

```
GateBox = 蓝图 × 对账 → 记录
```

**四层执行体系**（后面逐条定义）：

```
链（一项任务）
 └─ 步骤 = 对象 · 条件 · 组件 · 能力
      ├─ 组件：执行者内的一项功能（带配置与观测）
      └─ 能力：GateBox 施加的动作（控制 / 观测 / 加工）
执行者 = 插件（外部工具）| 核心（GateBox 本体）
```

### 1. 四层执行体系（定义表）

| 层 | 定义 | 例子 |
|---|---|---|
| **插件** | 一个可独立安装/升级、独立运行的**工具**；内部自治（黑盒），只透过输出/日志/状态露出 | caddy、acme.sh、docker、ddns-go、mosdns |
| **组件** | **执行者内的一项功能**（一项任务的封装）：对外提供配置项与观测来源，内部用若干能力完成 | docker·编排、ddns-go·更新解析、caddy·反向代理、核心·配置编译 |
| **能力** | **GateBox 能施加的动作**，通用且有限，分三族（控制 / 观测 / 加工） | 写配置、停止、删除、启动、重载、读日志、编译 |
| **链** | 由「组件 + 能力」的步骤**编排**成的一项任务 | 发布服务、更新编排、IP 巡检 |

**关系**：链 → 步骤（对象+条件+组件+能力）→ 组件 → 执行者（插件或核心）。

> **关键纠正**：能力**写在链上**——它是 GateBox 实际施加的操作。否则"更新 compose → 停止旧编排 → 删除容器 → 用新的启动"这些操作无处定义。

---

### 2. 插件（工具，黑盒）

**定义**：一个可独立安装/升级、独立运行的工具；内部过程**看得到但管不着**。

- **系统插件**：默认自带。例：caddy、acme.sh、docker。
- **外部插件**：后续安装。例：ddns-go、mosdns、flame、caddy-l4、coraza。

**黑盒原则**：插件的内部业务过程（如 ddns-go 的"取 IP → 比对 → 更新"）**不建模**；它通过**证据**（CLI 输出、日志、状态）露出来，用于 debug 与呈现。GateBox 对插件只做三件事：**配置、触发、观测**。

---

### 3. 执行者：插件 | 核心

链上每一步都由某个**执行者**执行。执行者有两类：

| 执行者 | 是什么 | 组件的性质 |
|---|---|---|
| **插件** | 外部工具 | 组件**操作工具**（如 docker·编排） |
| **核心** | GateBox 本体 | 组件**操作对象**（如核心·配置编译） |

**GateBox 核心（本体）定义** = GateBox 程序自身，系统的控制中枢，做五件事：

1. **受理声明**：蓝图、对象的编辑与保存。
2. **加工**：派生对象、编译配置、比对差异、校验。
3. **编排**：按链驱动组件、触发插件。
4. **观测**：收集证据（日志 / CLI 输出 / 状态），生成链日志。
5. **呈现**：地图 / 各页 / 日志界面。

**核心也有组件**：`核心·配置编译`、`核心·对象派生`、`核心·差异比对`。它们与插件组件并列，只是**操作对象而非工具**。这样**链上一切皆组件，无例外**。

> **例子：核心·配置编译**
> 读对象（服务、域名、证书、变量、片段）+ 现状（容器 IP、证书路径）→ 渲染出 Caddy 配置 → 写盘。
> 能力：读对象、渲染、写配置。观测：生成的配置文本、与上一版的差异、耗时。
> 它存在的意义：链上"编译配置"这一步要能**显示、记录、定位失败**（如某域名缺凭证导致编译失败），不能是黑洞。

---

### 4. 组件与自述

**定义**：执行者内的一项功能（一项任务的封装）。对外提供**配置项**与**观测来源**，内部用若干**能力**完成。

**自述（Manifest）**：每个组件自带一份声明，系统据此认识它、链据此选用它。含：所属执行者、配置项、能力、消费与产出、前置。

> **例子：docker 的「编排」组件**
>
> ```
> 执行者：docker（系统插件）
> 组件：编排
> 配置：compose 内容、项目名
> 能力：写配置、停止、删除、启动、读状态、读日志
> 消费：变量、端口；产出：容器（运行信息）
> ```

> **例子：ddns-go 的「更新解析」组件**
>
> ```
> 执行者：ddns-go（外部插件）
> 组件：更新解析
> 配置：二级域名、供应商、检查间隔
> 能力：写配置、重载（触发检查）、读日志
> 内部（不建模）：取公网 IP → 比对 → 更新，只从日志看到
> ```

**扩展性**：接入新插件/新功能 = 提供一份自述；链与地图自动可选它。

#### 4.1 类型目录：组件自述驱动 UI（自适应）

组件的自述里，除角色/能力外，还声明它**提供哪些"类型"**：

```yaml
组件: caddy（内置）
提供:
  service_types:       [reverse_proxy, file_server, redirect, respond]
  middleware_types:    [encode, basic_auth, headers, websocket, rewrite, code]
  entrypoint_protocols:[http, https]

组件: caddy-l4（外部插件）
提供:
  service_types:       [tcp_proxy, udp_proxy]
  entrypoint_protocols:[tcp, udp]

组件: frankenphp（外部插件，整包覆盖型）
变体: { component: caddy, feature: frankenphp }
提供:
  service_types:
    - { id: php, label: PHP 应用（FrankenPHP）,
        fields: [root, worker, php_version, env, extensions] }
  middleware_types: [php_worker]
```

**类型目录 = 所有组件自述的并集**，并标安装状态：

```yaml
catalog:
  service_types:
    - { id: reverse_proxy, from: caddy,       installed: true }
    - { id: tcp_proxy,     from: caddy-l4,    installed: false }
    - { id: php,           from: frankenphp,  installed: false }
```

**界面自适应**：类型**全部列出**，未安装的置灰 + 一键安装：

```
新增服务 → 选择类型
  ( ✓ ) 反向代理
  ( ⚠ ) TCP 转发     需安装 caddy-l4    [ 安装 ]
  ( ⚠ ) PHP 应用     需安装 frankenphp  [ 安装 ]
```

- **安装** → 下载插件 + 重建变体 + 重启 caddy + 注册类型（有过程记录）；
- **无该组件**时，用到该类型的服务标「依赖缺失」，提供 [重装] / [改类型]；
- **数据来源**：内置组件写死 + 在线索引（GateBoxStore，已签名）声明外部插件类型，所以**未安装也能列出并提示安装**；
- **变体组合**：多个整包覆盖型插件（frankenphp / caddy-l4）合并为一份 caddy 变体 features，卸载其一即重建为剩余。

同一机制还管：Service 类型、Middleware 类型、入口协议、能力、消费与产出。**模型里没有写死的类型清单。**

---

### 5. 能力（Capability）

**定义**：GateBox 能施加的**一个动作**。它是 GateBox 与执行者之间的通用动词表，**通用且有限**（十几项），分三族：

| 族 | 能力 | 作用对象 |
|---|---|---|
| **控制** | 写配置、校验配置、应用/重载、启动、停止、删除、重启、触发任务 | 组件 / 插件 |
| **观测** | 读状态、读日志、读指标、读数据 | 组件 / 插件 |
| **加工** | 编译、派生、比对、校验 | 对象（由核心提供） |

**要点**：能力是"怎么做"的最小可执行、可记录、可重试单位；**不是业务步骤**。业务步骤（"更新 DDNS IP"）是**组件**。

---

### 6. 链（Chain）

**定义**：由「组件 + 能力」的步骤**编排**成的一项任务。分两种：

| 种类 | 来源 | 例子 |
|---|---|---|
| **事务链** | BP 声明（配置时） | 「发布服务」「更新编排」「IP 巡检」 |
| **流量链** | Caddy 服务态投影（访问时） | 「访问 `flare`」：入口 → WAF → TLS → 路由 → 上游 → 响应 |

**触发（Trigger）**：链的一等属性，三类——**用户操作 / 定时器 / 事件**。

**步骤结构**：

| No | 对象 | 条件 | 组件 | 能力 | 说明 |
| -- | ---- | ---- | ---- | ---- | ---- |

- **对象**：作用在谁身上（一个实例或一类集合）。
- **条件**：满足才执行；不满足则**跳过**（记入 Run，不算失败）。
- **组件**：由哪个功能完成（隐含其执行者）。
- **能力**：施加的动作。
- **顺序**：由前置关系求解（可并行），不手排。**幂等**：重复执行安全，无变化记"跳过"。

#### 例子 A：发布任务（触发：用户）— **Caddy 主流程 + 分派子序列**

主序列只做「分派 / 汇聚 / 编译 / 加载 / 验证」；被分派的子序列各自跑到"期待值"就交回。

```
┌──────────┐      ┌──────────────────────────────────────────────────────────────┐
│ 用户发布 │ ---> │ publish_sequence   Caddy 主流程（发布服务）                   │
└──────────┘      ├────┬──────────────┬────┬─────────────────────────────────────┤
                  │ No.│  匹配条件    │ -> │  执行任务                           │
                  ├ ─ ─┼─ ─ ─ ─ ─ ─ ─ ┼ ─ ─┼ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┤
                  │ #0 │  始终        │ -> │  分派 docker_sequence：启动容器（并发）   │
                  ├ ─ ─┼─ ─ ─ ─ ─ ─ ─ ┼ ─ ─┼ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┤
                  │ #1 │  始终        │ -> │  分派 ddns_sequence：解析域名（并发）     │
                  ├ ─ ─┼─ ─ ─ ─ ─ ─ ─ ┼ ─ ─┼ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┤
                  │ #2 │  tls 开启    │ -> │  分派 acme_sequence：签发证书（等解析）   │
                  ├ ─ ─┼─ ─ ─ ─ ─ ─ ─ ┼ ─ ─┼ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┤
                  │ #3 │  期待值到齐  │ -> │  编译配置（路由 + 上游 + 中间件 → Caddyfile）│
                  ├ ─ ─┼─ ─ ─ ─ ─ ─ ─ ┼ ─ ─┼ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┤
                  │ #4 │  始终        │ -> │  加载生效（原子替换）               │
                  ├ ─ ─┼─ ─ ─ ─ ─ ─ ─ ┼ ─ ─┼ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┤
                  │ #5 │  始终        │ -> │  验证（可达 · 证书有效）            │
                  └────┴──────────────┴────┴─────────────────────────────────────┘

┌────────────────────────────────────────────────────────────┐   ┌────────────────────────────────────────────────────────────┐
│ docker_sequence   docker（后端）                            │   │ ddns_sequence   ddns（解析）                                │
├────┬──────────────┬────┬───────────────────────────────────┤   ├────┬──────────────┬────┬───────────────────────────────────┤
│ #0 │  始终        │ -> │  启动容器                           │   │ #0 │  始终        │ -> │  写入解析配置 + 重载              │
│ #1 │  容器运行    │ -> │  ◀ 期待：上游地址                   │   │ #1 │  解析生效    │ -> │  ◀ 期待：解析值                   │
└────┴──────────────┴────┴───────────────────────────────────┘   └────┴──────────────┴────┴───────────────────────────────────┘

┌────────────────────────────────────────────────────────────┐
│ acme_sequence   acme（证书）                                │
├────┬──────────────┬────┬───────────────────────────────────┤
│ #0 │  解析已生效  │ -> │  签发证书（HTTP-01）              │
│ #1 │  签发成功    │ -> │  ◀ 期待：证书文件                 │
└────┴──────────────┴────┴───────────────────────────────────┘
```

| 项 | 说明 |
|---|---|
| **主序列** | `publish_sequence` — Caddy 主流程，只做分派 / 汇聚 / 编译 / 加载 / 验证 |
| **子序列** | `docker_sequence` / `ddns_sequence` / `acme_sequence` — 被分派，跑到"期待值"交回 |
| **并发** | `#0 docker` 与 `#1 ddns` 同时发起；`#2 acme` 等 `ddns` 解析生效 |
| **汇聚点** | `#3 期待值到齐`（唯一硬等待点） |
| **内部流程** | 各子序列内部过程（启动日志 / ddns 日志 / acme CLI 输出）通过**证据**观测，不画进主序列 |

#### 例子 B：更新编排（触发：用户）

| No | 对象 | 条件 | 组件 | 能力 | 说明 |
| -- | ---- | ---- | ---- | ---- | ---- |
| #0 | 编排 | 始终 | 核心·差异比对 | 比对 | 发现 compose 有变更 |
| #1 | 编排 | 有变更 | docker·编排 | 写配置 | 写入新的 compose |
| #2 | 编排 | 有变更 | docker·编排 | 停止 | 停止旧编排 |
| #3 | 编排 | 有变更 | docker·编排 | 删除 | 删除相关容器 |
| #4 | 编排 | 有变更 | docker·编排 | 启动 | 用新 compose 启动 |
| #5 | 服务 | 容器变化 | 核心·对象派生 | 派生 | 从容器派生服务/上游 |
| #6 | Caddy 配置 | 始终 | 核心·配置编译 | 编译 | 重新编译 |
| #7 | Caddy | 始终 | caddy·反向代理 | 重载 | 加载生效 |

#### 例子 C：IP 巡检（触发：**定时器 5m**）

| No | 对象 | 条件 | 组件 | 能力 | 说明 |
| -- | ---- | ---- | ---- | ---- | ---- |
| #0 | 本机 | 始终 | ddns·更新解析 | 触发任务 | 触发 ddns 检查 |
| #1 | 路由（一类对象） | IP 有变化 | ddns·更新解析 | 读日志 | 内部更新见证据 |

> `ddns·更新解析` 同时出现在 A、B/C 里，说明"同一组件被不同场景复用"。

### 7. 观测模型（让"管不着"也能 debug）

**原则**：不穿透插件源码；配置、触发、观测与插件吐出的东西全部留痕并互相关联。

**三层**：

| 层 | 实体 | 记录什么 |
|---|---|---|
| **编排层** | Run / Step | 卡在哪一步、成败、耗时 |
| **动作层** | 调用 | 施加的能力：输入、命令/API、输出、退出码、耗时 |
| **证据层** | 证据 | 插件的原始输出：CLI stdout/stderr、日志、状态快照 |

**两种形态**（同一个模型，两种叠加）：

| 形态 | 位置 | 作用 |
|---|---|---|
| **链视图** | 地图 / 链页面 | 显示**最后一次状态**（每步最后执行时间、结果、耗时）；编排叠加 + 观测叠加 |
| **链日志** | 每条链一份独立日志 | 按时间倒序的历次 Run；下钻 Step → 调用 → 证据 |

**debug 例子（DDNS）：**

```
Run#1188  IP 巡检                                       [编排层]
 └ Step#1  更新解析（ddns-go）                           [编排层]
    ├ 调用  触发任务(ddns-go -once)     → 退出码 0，3.1s  [动作层]
    │   └ 证据 stdout:                                   [证据层]
    │        [12:00:01] ip = 1.2.3.5
    │        [12:00:02] app2.neob.cn: 1.2.3.4 → 1.2.3.5
    │        [12:00:03] updated ok
    └ 调用  读日志(ddns-go)             → 关联 3 行日志
```

### 8. 对账（Reconcile）

**语义**：让「现状」逼近「期望」的唯一动作。触发：被动（蓝图/对象变化）+ 主动（定时巡检、外部事件）。失败：标记 + 退避重试，不全局回滚。

---

### 9. 对象（Object）

**定义**：对象 = 组件**需要（消费）或产出**的东西。**对象清单由组件自述推导，不手工维护**——加一个组件/插件（声明它需要/产出什么），对象集自动扩展。

- **可寻址**（有身份、能被点名）的才是对象；只在流上传递、不可寻址的运行信息（如 label、公网 IP）不是对象。
- 分两类：
  - **源对象**：用户声明、进蓝图。例：服务、域名、端口、片段、变量、凭证、编排。
  - **派生对象**：组件产出、作现状。例：证书、容器、派生服务、解析记录。
- **粒度**（如"域名"是一行一个，还是并进服务）待定。

**由当前组件推出的对象清单**：

| 组件 | 需要（消费） | 产出 |
|---|---|---|
| caddy·反向代理 | 服务、域名、端口、片段、变量、证书 | 服务态 |
| acme·证书 | 域名、凭证 | 证书 |
| docker·编排 | 编排、镜像、变量、端口、仓库凭证 | 容器、派生服务、label |
| ddns·更新解析 | 域名、凭证、公网 IP | 解析记录 |
| core·配置编译 | 服务、域名、证书、变量、片段 | Caddy 配置 |

→ 对象总集 = 两栏并集去重（**可寻址者**才算）。

**扩展规则**：将来"配置/调用 docker 网络"时——
- 只想**操作**网络（建/连/删）：那是 **docker·网络 组件的「能力」**，网络不必是对象；
- 要网络**保持某状态**：某组件声明"我需要网络"（并给出 spec 字段与 status 来源），网络**自动进入对象集**，蓝图可声明、链可作用、现状可观测。

| 环节 | 是否自动 | 谁提供 |
|---|---|---|
| 类型进入对象集 | ✅ | 组件声明"我需要它" |
| 能编辑（`spec` 字段） | ⚠ 需 schema | 声明它的组件（或中央注册表） |
| 能观测（`status` 来源） | ⚠ 需来源 | 声明它的组件 |

#### 9.1 部署单元：内容分两部分

**原则**：compose 文件是 **docker 的输入**，不是 GateBox 的对账对象。GateBox 的声明部分**复用 caddy 那套对象**（服务 / 路由 / 中间件），不新造概念。

| 部分 | 对象 | 谁用 | 来源 |
|---|---|---|---|
| **① docker 内容** | `deployments[].compose` | docker | **模板生成** / **手工填写** |
| **② GateBox 声明** | `services` / `routers` / `middlewares` | GateBox | 用户写 / 模板默认值展开 |
| 链接 | `backend: { deployment, port }` | — | 服务引用部署的容器端口 |

```yaml
# ── ① docker 内容（docker 所需）──
deployments:
  - name: flare-home
    host: nas
    compose:
      template: flare                 # 或 manual: |
      inputs: { title: HomeLab }

# ── ② GateBox 声明（与 caddy 反代同一种对象）──
services:
  - name: flare-web
    type: reverse_proxy
    backend: { host: nas, deployment: flare-home, port: 5005 }

routers:
  - name: flare
    host: flare
    roots: [neob.cn]
    entrypoint: https
    port: 443
    service: flare-web
    middlewares: [gzip]
    tls: auto
```

**模板同时提供两部分的默认值**：

```yaml
# Store 模板：flare
id: flare
inputs:
  - { key: domain, type: domain, required: true }
  - { key: title,  type: text,   default: "我的导航" }
service: { type: reverse_proxy, containerPort: 5005 }          # 声明默认
router:  { protocol: https, port: 443, tls: auto, middlewares: [gzip] }
compose: |                                                     # docker 内容模板
  services:
    flare:
      image: soulteary/flare:latest
      ports: ["{{hostPort}}:5005"]
      volumes: ["./data:/app/data"]
```

**用户只写**：

```yaml
deployments:
  - { name: flare-home, host: nas, template: flare,
      inputs: { domain: flare.neob.cn, title: HomeLab } }
```

**GateBox 展开成标准对象**（交给既有编译/发布链）：

```yaml
services:
  - { name: flare-home, type: reverse_proxy,
      backend: { host: nas, deployment: flare-home, port: 5005 } }
routers:
  - { name: flare-home, host: flare, roots: [neob.cn],
      entrypoint: https, port: 443, service: flare-home, middlewares: [gzip], tls: auto }
```

**结论**：
- compose 文件是**产物 / 输入**（模板生成或手填），不是真相；
- GateBox 声明部分**就是 服务 / 中间件**——手工反代与模板应用产出同一套对象；
- **不写 label、不写 caddy 配置**。

### 10. 蓝图（Blueprint，BP）——约定已定，结构待重写

**语义**：整个网关「应该长什么样」的唯一真相；持久、可 diff、可回滚。装：组件（引用已装插件/核心的自述）、对象、链。

| 已定约定 | 决定 |
|---|---|
| 核心组织 | **对象与链分离**：对象声明"要什么"，链声明"怎么做" |
| 用户自定义链 | **混合**：内置链覆盖常见操作；高级用户可基于已有组件+能力拼装 |
| 派生对象 | **不进蓝图**：蓝图只存**源头**；派生结果由观测得，作 `status` |
| 组件自述 | **只读 + 可覆盖**：自述由插件/核心自带、用户不可改；用户可禁用能力、选择实现、调参数 |

> 蓝图结构（组件册 / 对象册 / 链册）待"对象""链"讨论完成后重写。

### 11. 记录（Run）

每次对账/访问留下的痕迹。一次 Run 含若干 Step，Step 含若干调用与证据；Run 携带**上下文**用于步骤间传值（早期的"载体"即此，属记录层）。

---

### 12. 不变量

1. **请求与控制分离**：控制不处理访问；访问路径不驱动外部系统。
2. **单向访问路径**：一次访问只读服务态，不回写期望。
3. **状态有源**：`spec` 由蓝图展开、`status` 由观测。
4. **持续收敛**：对账让现状持续逼近期望，并检测漂移。
5. **原子服务态**：Caddy 配置更新不允许中间态对外可见。
6. **可解释**：每个状态变化可追溯到 Run → Step → 调用 → 证据。
7. **链可见**：每次事务、每次访问都产出一条有序、可展示、可追溯的记录。

**执行体系**：

| 概念 | 中文 | 英文 | 缩写 |
|---|---|---|---|
| 蓝图 | 蓝图 | Blueprint | BP |
| 插件 | 插件 | Plugin | — |

**对象命名（对齐 Traefik）**：

| 对象 | 中文 | 英文 | 对应标准 |
|---|---|---|---|
| 入口点 | 入口点（协议 → 端口，一对多） | EntryPoint | Traefik EntryPoints |
| **项目** | **多个服务组成的组合（一份 compose / 一份编排）** | Project | — |
| **服务** | **编排中的一项（一个容器 / compose 的一个 service）；可发布多个端口 → 含多条路由** | Service | Traefik Service |
| **路由** | **一个转发，后端为 1 个端口**（含 域名 / 入口点+端口 / 中间件 / TLS / 类型 / 后端） | Route | Traefik Router |
| 中间件 | 中间件 | Middleware | Traefik Middlewares |
| 主机 | 主机（多主机管理） | Host | — |
| 域名 | 域名（根域名 + 凭证） | Domain | GateBox 特有 |
| 凭证 | 凭证（DNS / 仓库） | Credential | GateBox 特有 |

> **旧名替换**：二级域名 → **入口/服务**；片段 → **中间件**；端口表 → **入口点**；应用 → **分组**（可选，纯标签）。
> **层级**：**项目 → 服务 → 路由**；网关页列的是**路由**。以 [`docs/v4.1/views.md`](../v4.1/views.md) §5 · [glossary](../glossary.md) 为准。
> **修订**：**拆开 Router / Service**——"服务"是编排中的一项（一个容器，可含多条路由），"路由"是一个转发（后端 = 1 个端口）。原"服务合并接入+后端"的写法**作废**。

### 14. 与 ADR-040 / ADR-041 的关系

- V4 的「依赖图 / 事实注册表 / 双层投影」不再是前端主视图；"依赖求解"保留为链顺序的底层。
- ADR-042 把"统一描述"具体化为 **四层执行体系（插件/组件/能力/链）+ 对象 + 蓝图 + 记录**，并纠正"只有网状图、没有链与记录"的缺陷。
