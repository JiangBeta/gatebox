# ADR-015：Compose 三层领域模型与项目标识

- 状态：已接受
- 日期：2026-08-25

## 背景

原文档存在一处不自洽：PRD 第 7 节写 `appData/<appName>/docker-compose.yaml`，暗示「一个 App = 一个 compose 文件」；但术语表定义 App 为「**可被代理的最小单元**」，而一个 compose 通常起多个 service（如 jellyfin + postgres），其中往往只有一个需要被代理。两个定义不可能同时成立。

## 决策

### 1. 三层模型

```
ComposeInstance (1) ──< Container (N) ──< App (M, M ≤ N)
```

只有需要被代理的容器升格为 App。这是「一个 compose 起 3 个容器、其中 2 个各自代理到不同域名」的唯一自洽建模，也是应用商店（一个商店应用 = 一个 compose）与多主机（compose 是部署单位）的落点。

### 2. 项目标识

- **主键 = `projectName`**，格式 `[a-z0-9][a-z0-9_-]{1,62}`（docker compose 硬约束），**不引入随机 ID**——它同时是 docker 项目标识、`appData/` 目录名、Caddyfile 引用名，多一层映射只是负担。
- **`displayName`** 独立字段承载任意字符（中文）展示名。
- **`projectName` 创建后不可改**，UI 不提供改名入口。改项目名在 docker 眼里等于换了个全新项目，旧容器不会被 down、直接变孤儿——该硬约束应诚实暴露，而非用假的「改名」按钮掩盖。

### 3. 真相源

**磁盘上的 YAML 文件是唯一真相源**，BoltDB 只存元数据与指针（与 caddy / ddnsgo「改写配置文件」的处理方式一致，不在 DB 里存影子副本）。打开编辑器时永远重新读盘。另存 `lastDeployedYAML`（上次成功部署内容）供用户**主动**恢复，无任何自动回滚行为。

### 4. 容器三态

`托管`（GateBox 在 `appData/` 下创建）/ `外部编排`（`docker compose ls -a` 发现的非托管项目，默认只读）/ `游离`（无 compose label）。

项目发现用 **`docker compose ls -a`** 而非扫容器 label——前者能列出**已停止的项目**并给出配置文件绝对路径；只扫 running 容器会让用户 stop 掉的项目从界面凭空消失。

## 后果

- 优点：容纳多 service compose 的真实场景；应用商店与多主机有天然落点；标识唯一且可读。
- 代价：`appData/<appName>/` 需正名为 `appData/<projectName>/`（ADR-011 已更新）；不提供改名功能会有少量用户困惑，需在 UI 上说明。
- 约束：仅 ComposeInstance 带 `hostID`（默认 `local`）为多主机预留；容器/镜像/网络/卷是运行时对象，不落库、不加字段。
