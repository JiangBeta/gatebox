# ADR-038：核心组件配方变体与制品矩阵

- 状态：已接受
- 日期：2026-09-16
- 前置：ADR-027（永不改写配方）、ADR-030（核心/插件分类）、ADR-036（扩展平台）、ADR-037（主程序与插件分离）
- 后续：ADR-039（插件运行时契约）

## 背景

「核心插件扩展」类插件的本质是**给核心组件补充编译期模块**。Caddy 是 Go 程序，模块必须在编译期链接，因此：

- `caddy-l4` 今天安装即把 `$DATA_DIR/tools/caddy/caddy` 整体替换为含 l4 的构建（`plugin.go:257-268`）；
- 若同时启用 `coraza`，它的制品是另一个 Caddy 构建——**最后一个赢，前一个被静默破坏**；
- ADR-027 规定 GateBox **永不改写配方**（不本地编译），只能搬运预构建制品；
- 已核实：Caddy 官方构建服务器 `caddyserver.com/api/download` **无 SLA、封自动化（curl/wget）、仅供人工一次性下载**，且上游正在移除依赖它的 `add-package`/`remove-package`/`upgrade` 命令，官方推荐 `xcaddy` 或预构建 Release。**运行时依赖该服务不可接受。**

因此需要一个既不本地编译、又不依赖无 SLA 上游服务的多模块共存方案。

## 决策

### 1. 中性特征声明（`component-variant` 扩展点）

新增扩展点 **`component-variant`**：插件声明它给某个核心组件增加的**中性特征**，特征值是稳定标识（Go 模块路径或等价 ID），**不是插件 ID、不是插件专有术语**：

```yaml
# caddy-l4 的贡献
contributions:
  capabilities:
    - point: component-variant
      data: { component: caddy, feature: "github.com/mholt/caddy-l4" }
```

```yaml
# coraza 的贡献
contributions:
  capabilities:
    - point: component-variant
      data: { component: caddy, feature: "github.com/corazawaf/coraza-caddy/v2" }
```

- 守 I1：核心只认识「特征集合」，不认识 `layer4` / `coraza`；
- 组件适配层（caddy 属核心组件，允许组件专有逻辑）负责把「特征集合」翻译为变体键与制品解析，**但不得出现插件 ID**。

### 2. 变体键与解析

内核把**已启用插件的特征取并集**，与组件版本、平台一起规范化成变体键：

```
variantKey = hash(
    component   = caddy
    version     = 2.10.x            # 满足全部启用特征约束的组件版本
    os / arch   = linux / amd64
    features    = sort([github.com/corazawaf/coraza-caddy/v2,
                        github.com/mholt/caddy-l4])
)
```

解析流程：`variantKey → 查 Store index.json 的 variants[] → 命中则下载 / 校验 sha256 / 原子替换 / 重启 / 健康检查 / 失败回滚`。

### 3. 配方重算触发点

配方**只在启用集合变化时重算**（不在请求时、不在启动时盲算）：

- 启用 / 停用 / 安装 / 卸载任何 `component-variant` 插件 → 重算特征并集 → 解析新变体 → 替换核心组件二进制 → 重启该组件 → 健康检查。
- 失败回滚：保留旧制品于 `versions/`，健康检查失败则回滚到上一可用变体。
- UI 需明示代价：「启用该插件将切换 Caddy 制品并重启 Caddy（约 N 秒）」。

### 4. 制品矩阵 + 按需 CI 构建

- **构建不在设备上，也不在上游服务上**：由 **GateBoxStore CI（GitHub Actions + `xcaddy`）**构建变体，产出签名 tar.gz 发布到 GitHub Releases；
- **制品矩阵**：`index.json` 的 `variants[]` 列出已发布变体（`key / component / version / features / os / arch / url / sha256`）；
- **按需构建**：命中不到的组合，UI 提供出口——触发 Store 的按需构建 workflow（异步，构建完成后再安装），或导入自定义制品（`custom` 源，ADR-027 已允许）；
- 常用组合（纯核心、+l4、+coraza、+l4+coraza）应预构建，保证离线/低资源场景可用。

### 5. 版本约束仲裁与冲突拒绝

- 每个特征声明其组件版本约束（如 `caddy >=2.10 <2.11`）；
- 内核求解满足**全部**启用约束的组件版本；无交集时**拒绝同时启用**并给出中文冲突说明（列出冲突双方与各自约束）；
- 变体键包含组件版本，避免跨版本误用制品。

### 6. 整包覆盖型与互斥兜底

- 插件**默认只声明 feature**，不携带整包二进制；
- 若发布者提供整包组件二进制（如私有 fork 的全量构建），该插件标记为**互斥**：与同组件的其他变体插件不可同时启用，UI 明确提示；
- 禁止在设备端合并整包二进制与特征协商两种来源。

### 7. 缓存

变体制品缓存于 `$DATA_DIR/tools/<component>/versions/<variantKey>/`：组合来回切换（L4+Coraza ⇄ 仅 L4 ⇄ 纯核心）不重复下载。

## 本阶段实现边界

**实现**：`component-variant` 扩展点、变体键计算、特征并集重算、Store `variants[]` 解析与下载、版本约束仲裁、互斥兜底、`versions/` 缓存、Store CI 的 xcaddy 变体构建。

**预留不实现**：按需构建 workflow 的 UI 触发（先提供手动触发入口）、变体制品的可复现构建证明（reproducible builds / attestation）。

## 后果

- 优点：多模块共存不再互相破坏；内核不编译、不依赖无 SLA 上游；组合切换可缓存、可回滚；配方与制品解耦，插件作者只声明特征。
- 代价：引入特征并集求解与组件版本仲裁；Store 需维护变体矩阵与构建 CI；小众组合首次启用需等待构建；特征是组件级概念，各核心组件需分别定义「可变特征」的翻译规则。

## 补充 2026-09-16：实现进展

**已实现**：

- `component-variant` 扩展点；`extension.VariantKey` / `Registry.ComponentFeatures`（与 Store 的 `gbx-store variant-key` 同算法，单测锁定同值）。
- `component.ApplyVariant`：算键 → 拉索引匹配 → 下载校验 → `source.InstallVersioned` 落 `versions/<key>/`；同变体跳过避免重复下载。
- 启用/停用/卸载 `component-variant` 插件后，自动重算特征并集、替换变体并重启组件（best-effort）。
- Store 侧：`scripts/build-variant.sh` + `build-variant.yml`（xcaddy，按特征并集构建）。

**仍未实现**：变体按需构建的 UI 触发（现为手动 workflow / API）、可复现构建与证明、各组件「可变特征」翻译规则的显式清单。
