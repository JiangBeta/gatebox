# ADR-035：变量统一至设置页

- 状态：已接受
- 日期：2026-09-15
- 前置：ADR-018（GateBox 变量系统）、ADR-033（变量接线）、ADR-025（一级导航与「容器」更名）
- 参考：`docs/gateway.md` §5.1、`docs/docker.md`、`docs/layout.md` §3、`docs/home.md` §3

## 背景

GateBox 存在两套完全独立、却几乎同构的「变量」系统：

| | 网关变量 | 容器变量 |
|---|---|---|
| 存储 | bucket `variables` | bucket `container_variables` |
| 引用写法 | `<%KEY%>` | `${KEY}`（compose 原生） |
| 内建 | 6 个 `GB_*`（只读，上下文派生） | `GB_PROJ_NAME` / `GB_PROJ_FILE` / `GB_SER_<n>_PORT_<n>` |
| 数据模型 | `model.Variable` | 复用 `model.Variable` |
| 键名校验 | `validVariableKey` | 复用同一函数 |
| 替换时机 | Caddyfile 生成时**实时**查表 | compose **保存时**破坏性替换写盘 |
| 未命中 | **报错**（阻止非法 Caddyfile） | **原样透传**给 compose |

两套系统共享模型与校验，却各自维护 bucket、API 与前端 Tab（网关页、容器页各有一个「变量」入口）。管理入口重复，而「一套命名值」才是用户的心智模型。本 ADR 定案将两者合并到「设置 → 变量」。

## 决策

### 1. 单一存储 + 统一 API

- 用户变量合并进单 bucket `variables`；容器桶 `container_variables` 废弃。
- 唯一入口：`GET/POST /api/v1/settings/variables`、`PUT/DELETE /api/v1/settings/variables/{key}`。
- 删除 `/api/v1/gateway/variables`（用户变量）与 `/api/v1/docker/variables`（用户变量）。
- 系统变量收口为 `GET /api/v1/settings/variables/system`，后端统一返回两侧系统变量的**描述符**（key / 引用写法 / 说明 / 适用上下文）；前端不再硬编码容器内置。`GB_SER_<n>_PORT_<n>` 是派生模式、无法枚举，以「模式说明」返回。

### 2. 不引入 scope 字段

- `model.Variable` 保持 `key`（主键）/`value`/`description`/`createdAt`，不新增作用域、默认值、密文字段。
- 代价是已知的：同一 key 在网关与容器只能有一个值，且两个编辑器的用户变量选择器会互相展示对方的变量。这是本决策明确接受的取舍（见「后果」）。

### 3. 键名规则收敛

- 统一为 `[A-Za-z_][A-Za-z0-9_]*`：不允许连字符、不允许数字开头。
- 理由：compose 的 `${...}` 语法硬约束；统一存储后，任何键都必须能被两个上下文消费，消除「合法但容器用不了」的键。
- 该规则同时修正代码（原允许 `[A-Za-z0-9_-]`）与 `docs/gateway.md` 的既有不一致。
- 键大小写维持现状：前端输入即大写、后端大小写敏感，不做强制归一。

### 4. 引用写法保持双轨（不统一区隔符）

- **网关**：`<%KEY%>`（GateBox 自定义）。**容器**：`${KEY}`（compose 原生）。
- 明确**拒绝**把网关也改为 `${KEY}`：
  - `{$X}`（Caddy 环境变量）与 `${X}` 仅差字符顺序，二者会同时出现在同一 Caddyfile 中、由不同主体解析，是易写错且写错后静默生效的转置陷阱；`<%X%>` 一眼可辨。
  - compose 的 `${X}` 自带 docker 语义（`${X:-默认}`、`${X:?错误}`、`.env`、宿主环境回退），GateBox 在网关侧无法等价复用，字面统一并不等于语义统一。
  - 字面 `${…}` 在 Caddyfile 中需额外转义规则。
- 因此「变量」是**命名值**（统一存储、统一管理），「引用写法」是**消费格式的语法**（随上下文而变）。

### 5. 未命中行为保持上下文各自

- 网关 `<%X%>` 未命中**报错**（Caddyfile 无 `.env`/环境回退，fail-fast 是唯一安全选择）。
- 容器 `${X}` 未命中**原样透传**给 docker compose（保留 `.env`/宿主环境回退）。
- `scope` 虽不落模型，「上下文语义」仍由引用写法承载。

### 6. 写操作一律触发 Caddy reload

- 任何用户变量的写操作都执行 `reloadCaddy`，不区分用途。实现最简、网关侧永远新鲜；仅容器用途的改动多一次无害重载（前端沿用长超时）。

### 7. 插值时机不统一（已知债务）

- 网关变量实时替换；容器变量在保存 compose 时破坏性替换写盘，改变量**不回溯**已有编排。
- 本次**不修**插值时机：存量 compose 文件中的占位符已丢失、无法恢复，根治需引入「模板层」，属独立工程。
- 设置变量页须明确标注「容器侧改动仅对之后新建 / 重新保存的编排生效」，并把「插值时机统一」登记为已知债务。

### 8. 迁移：自动、可见、可回滚

- 服务启动时执行一次性迁移（meta 标记保证幂等）。
- 同名不同值 → **不静默裁决**，列入迁移冲突报告，不自动导入，由用户在设置页就地解决。
- 键名不合法的存量键 → 同样列入冲突报告、不自动导入，用户重命名并同步改引用。
- 旧 bucket **保留只读备份**，使回滚成为可能。

### 9. 前端：设置页新增右上 Tab

- 设置页采用与网关/容器页一致的右上 Tab 机制（`route.meta.tabs` + `?tab=`）：`常规 | 变量`，默认 `常规`。
- 移除网关页、容器页的「变量」Tab；两个编辑器（Caddy 片段 / compose）保留**内联新增变量**，改调统一 API。
- 变量页布局分两段：**用户变量**一张可编辑表格；**系统变量**另设只读小节，按「网关内置 / 容器内置」分组。

### 10. 术语（统一语言）

- 总称**变量**；分**用户变量**（可编辑、统一存储、两处可引用）与**系统变量**（只读、上下文派生）。
- **引用写法**分 `<%KEY%>`（网关）与 `${KEY}`（容器）。
- compose 服务级的 `environment:` 键值仍称**环境变量**，与本次全局「变量」明确区分。
- 不使用 scope 一词。

## 范围与例外

- 不改变系统变量的解析规则（`GB_APP` 等仍按服务上下文运行时解析）。
- 不改变 Caddyfile 生成与 compose 部署的任何流程，仅改变量数据的来源与入口。
- 容器插值时机维持现状（§7）。

## 后果

- **优点**：变量单一数据源与单一管理入口；消除前后端重复的内置变量定义；键名规则自洽；区隔符与既有 ADR-018/033 一致，无破坏性语法迁移。
- **代价**：
  - 无 scope ⇒ 同键异义只能取一值；两个编辑器选择器互相污染，需靠命名约定缓解。
  - 迁移与冲突处理引入一次性复杂度（幂等标记 + 冲突报告 + 旧桶备份）。
  - 容器变量改动不回溯，是必须向用户明示的已知债务。
- **需同步文档**：`docs/gateway.md`（Tab 与 §5.1）、`docs/docker.md`（变量入口与接口）、`docs/layout.md` §3（设置 Tab、移除网关变量 Tab）、`docs/home.md` §3（设置页）、`docs/glossary.md`（新增术语）。

## 补充 2026-09-15：托管项目目录唯一真源

- **唯一真源**：托管项目目录恒为 `compose.ManagedDir(project)` = `<dataDir>/appData/<project>`（`compose.ManagedRoot()` = `<dataDir>/appData`）。`docker_compose.go`（`isManagedConfig` / 列表兜底 / `scanManagedProjects`）与 `docker_variables.go`（`GB_PROJ_FILE`）一律由它派生，不再手写 `filepath.Join(dataDir,"appData",…)`。
- **容器侧新增 `GB_DATA_DIR`**：值与网关 `<%GB_DATA_DIR%>` 相同（运行时数据根目录，绝对路径），可在 compose 中 `${GB_DATA_DIR}` 引用。
- **`GB_PROJ_FILE` 语义**：`= <GB_DATA_DIR>/appData/<GB_PROJ_NAME>`，**不含结尾 `/`**（便于 `${GB_PROJ_FILE}/<子目录>/` 组合、且避免被 docker 当命名卷）；描述与注释统一为该公式。
